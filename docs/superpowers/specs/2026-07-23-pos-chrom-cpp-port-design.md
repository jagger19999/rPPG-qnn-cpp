# POS and CHROM C++ Port Design

## Status

Approved for implementation on 2026-07-23. The user explicitly selected POS and
CHROM as the next traditional algorithms to port from the Python project.

## Goal

Add real POS and CHROM implementations to the independent C++ runtime so a bench
operator can select `green`, `pos`, or `chrom` with `--traditional`. Preserve the
existing timestamp-aware capture, ten-second/one-second window schedule, quality
gates, FFT heart-rate estimator, asynchronous result writer, and four-file package.

## Non-goals

- Do not port LGI, CONSENSUS, router/VQA, or additional Toolbox algorithms.
- Do not change EfficientPhys, ONNX, QNN, camera, ROI, or deep-worker behavior.
- Do not run more than one traditional algorithm at the same time.
- Do not add Python, SciPy, Eigen, model files, or generated vectors to the package.

## API and data flow

Introduce `TraditionalPredictor`, constructed with `green`, `pos`, or `chrom`.
Keep `GreenPredictor` as a source-compatible alias using the default GREEN method,
so existing tests and callers remain valid.

```text
mean BGR ROI + monotonic timestamp
              ↓
shared RGB sample history (30 seconds maximum)
              ↓
latest 10 seconds resampled to 300 RGB samples at 30 FPS
              ↓
     GREEN | POS | CHROM raw BVP
              ↓
existing finite checks, normalization, linear detrend, Hann spectrum
              ↓
HeartRateResult with method GREEN | POS | CHROM
```

The pipeline creates exactly one predictor from `config.traditional`. A method
switch requires a process restart, which clears the window and prevents mixed
method state.

## Mathematical contract

The pure BVP functions reproduce `src/rppg_cabin/traditional.py` at the fixed
runtime rate of 30 FPS.

### GREEN

Preserve the existing behavior. Normalize the green channel by its window mean.

### POS

- Use a 48-sample sliding window (`ceil(1.6 * 30)`).
- Normalize each RGB window by its channel means.
- Project with `[[0, 1, -1], [-2, 1, 1]]`.
- Combine as `s0 + std(s0) / std(s1) * s1` and overlap-add after demeaning.
- Apply smoothness-priors detrending with lambda 100.
- Apply the Python implementation's first-order 0.75–3.0 Hz zero-phase Butterworth
  filter using frozen double-precision coefficients for 30 FPS.

### CHROM

- Use an even 48-sample window with 24-sample overlap.
- Normalize each window by channel means.
- Form `x = 3r - 2g` and `y = 1.5r + g - 1.5b`.
- Apply the Python implementation's third-order 0.7–2.5 Hz zero-phase Butterworth
  filter using frozen double-precision coefficients for 30 FPS.
- Combine `x - std(x) / std(y) * y`, multiply by a symmetric Hann window, and
  overlap-add exactly as the Python baseline.

Zero-phase filtering uses the same odd extension, default pad length, steady-state
initial conditions, forward pass, and reverse pass as SciPy `filtfilt`. All
denominators use the Python baseline's finite epsilon behavior.

## Failure behavior

- Configuration accepts only `green`, `pos`, and `chrom`; other values remain a
  stable `CONFIG_INVALID` error.
- A non-finite BGR value, non-finite timestamp, or non-monotonic timestamp resets
  the complete method state and reports `sampling`.
- Low source FPS, capture gaps, flat/degenerate signals, and non-finite intermediate
  values use the existing invalid-result path; no method silently falls back to
  GREEN.
- The selected method is always present in invalid and valid result records.
